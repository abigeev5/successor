## 2. Продукт

### 2.1 Проблема
Значительная часть знаний сотрудника нигде не записана: исключения, обходные пути, «по каким признакам понимаю, что можно отправлять», к кому идти. Когда человек уходит (пенсия, декрет, увольнение, перевод), преемник месяцами восстанавливает это заново. Эксперт сам инструкцию не напишет: некогда, и половину знаний он не осознаёт.

### 2.2 Решение
Платформа передачи дел:
1. **ИИ-интервьюер** ведёт с экспертом структурированные беседы (текст или голос) по методике когнитивного анализа задач и вытаскивает неявное знание.
2. **Запись экрана с комментарием**: эксперт делает работу и проговаривает вслух, система превращает запись в пошаговую инструкцию со скриншотами.
3. Из бесед и записей система извлекает **карточки знаний**, каждая со ссылкой на точный фрагмент источника.
4. **Эксперт проверяет** каждую карточку: правит, подтверждает или отклоняет. В базу попадает только подтверждённое.
5. **Ассистент преемника** отвечает на вопросы только по подтверждённым карточкам, с цитатами. Нет источника — честный отказ, вопрос уходит в очередь «пробелов».
6. **Панель руководителя** показывает карту рисков: какие процессы держатся на одном человеке и насколько полно знание уже сохранено.

### 2.3 Роли
| Роль | Кто | Что делает |
|---|---|---|
| `manager` | руководитель подразделения | создаёт «передачу дел», видит прогресс и карту рисков, видит пробелы |
| `expert` | уходящий/ключевой сотрудник | даёт согласие, проходит интервью, записывает экран, проверяет карточки, отвечает на пробелы |
| `successor` | преемник/новичок | задаёт вопросы ассистенту, смотрит карточки и инструкции, оценивает ответы |
| `admin` | администратор | пользователи, подразделения, настройки |

Один пользователь может иметь разные роли в разных передачах дел; в MVP достаточно одной глобальной роли на пользователя + привязки к передаче дел (см. 7.1).

### 2.4 Главный сценарий (end-to-end, его же показываем в демо)
1. Руководитель создаёт **передачу дел**: эксперт, преемник, подразделение, причина, дедлайн.
2. Эксперт входит, читает и принимает **согласие** на запись и обработку.
3. Эксперт проходит **интервью** (20–30 минут, можно в несколько сессий). Справа видит, какие процессы и аспекты уже покрыты.
4. Эксперт делает **запись экрана** одного процесса, комментируя вслух.
5. Система в фоне создаёт **черновики карточек**. Эксперт в режиме проверки видит карточку рядом с источником (цитата или видео с нужной секунды), правит и подтверждает.
6. Преемник задаёт вопросы **ассистенту**, получает ответы со ссылками; клик по ссылке открывает карточку или видео на нужном моменте.
7. Преемник задаёт вопрос, ответа на который в базе нет → ассистент отказывается отвечать, вопрос попадает в **пробелы** → эксперт отвечает → ответ становится новой карточкой (после подтверждения).
8. Руководитель открывает **панель**: прогресс передачи, покрытие процессов, карта рисков, метрики.

## 3. Объём MVP

### Must (без этого демо не работает)
- Аутентификация, роли, сущность «передача дел», процессы.
- Согласие на запись (фиксация версии текста и времени), удаление своих данных.
- ИИ-интервьюер: текстовый режим + голосовые ответы (запись в браузере → распознавание → эксперт правит текст → отправляет).
- Отслеживание покрытия аспектов по процессам.
- Извлечение карточек из интервью с проверкой, что цитаты реально есть в источнике.
- Экран проверки карточек экспертом.
- Ассистент преемника: гибридный поиск, ответ с цитатами, проверка обоснованности, отказ, пробелы.
- Панель руководителя: прогресс, покрытие, карта рисков, базовые метрики.
- Eval-скрипт качества ассистента на демо-наборе.
- Демо-данные и `make seed-demo`.
- docker-compose для локального запуска.

### Should (сделать к спринту 2)
- Запись экрана в браузере или загрузка видеофайла → транскрипт → шаги → скриншоты → карточка-инструкция.
- Автоматическое размытие персональных данных на скриншотах.
- Журнал аудита.
- Учёт времени эксперта и преемника (нужен для финмодели).
- Запуск LLM локально (vLLM/Ollama) профилем docker-compose.

### Won't (не делаем в MVP, упоминаем в питче как развитие)
SSO/AD, интеграции с 1С/СЭД/мессенджерами, мобильное приложение, синтез речи интервьюера, мультиарендность SaaS, автоматические действия в чужих системах.

```
                       │  backend (FastAPI) │◄──────►│ PostgreSQL + pgvector │
                       └───┬──────────┬─────┘        └──────────▲───────────┘
                           │ jobs     │ LLM/embeddings          │
                       ┌───▼──────────▼───┐                     │
                       │      worker       │─────────────────────┘
                       │ ASR · ffmpeg · OCR│
                       │ PII · извлечение  │
                       └───┬──────────┬────┘
                           │          │
             ┌─────────────▼──┐   ┌───▼──────────────────────────┐
             │ файлы: /data   │   │ LLM: OpenAI-совместимый API   │
```

### 4.2 Стек
| Слой | Технологии |
|---|---|
| Backend | Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy 2 (async), Alembic, `uv` или `poetry` для зависимостей |
| БД | PostgreSQL 16 + pgvector (векторный и полнотекстовый поиск в одной базе) |
| Очередь задач | собственная очередь на таблице `jobs` (`SELECT … FOR UPDATE SKIP LOCKED`) + отдельный процесс `worker`. Без Celery/Redis |
| LLM | OpenAI-совместимый HTTP API (vLLM, Ollama, LM Studio и т.п.) + отдельный адаптер GigaChat |
| Эмбеддинги | `sentence-transformers`, модель по умолчанию `BAAI/bge-m3` (мультиязычная, 1024 измерения) |
| ASR | `faster-whisper` (по умолчанию), опционально GigaAM |
| Видео/аудио | `ffmpeg` |
| OCR | EasyOCR (ru+en) или Tesseract (`rus`) |
| NER для ПДн | `natasha` (имена), регулярные выражения (телефоны, email, СНИЛС, ИНН, паспорт, номера карт) |
| Нечёткое сравнение | `rapidfuzz` |
| Frontend | React 18 + Vite + TypeScript, React Router, TanStack Query, Tailwind CSS, shadcn/ui, `react-markdown` |
| Инфраструктура | Docker Compose, Makefile, pytest, ruff, mypy (мягко), eslint + prettier, vitest (минимально) |

**Не использовать** LangChain/LlamaIndex и подобные тяжёлые фреймворки: тонкие собственные обёртки проще отлаживать и контролировать.

### 4.4 Docker Compose
Сервисы:
- `db` — `pgvector/pgvector:pg16`, volume `pgdata`;
- `backend` — FastAPI на `:8000`, при старте `alembic upgrade head`;
- `worker` — тот же образ, команда `python -m app.worker`; содержит ffmpeg, faster-whisper, OCR;
- `frontend` — сборка Vite + nginx на `:3000`, проксирует `/api` на backend;
- `llm` — **профиль** `local-llm` (`docker compose --profile local-llm up`): vLLM или Ollama с моделью из `.env`; без профиля используется внешний `LLM_BASE_URL`.

Volume `appdata` монтируется в `/data` у backend и worker (файлы записей, скриншоты).

## 5. Модели и провайдеры

### 5.1 Интерфейсы
```python
class LLMProvider(Protocol):
    async def complete(self, messages: list[Message], *, temperature: float = 0.2,
                       max_tokens: int = 1024) -> str: ...
    async def complete_json(self, messages: list[Message], schema: type[BaseModel],
                            *, temperature: float = 0.0) -> BaseModel: ...
    async def stream(self, messages: list[Message], **kw) -> AsyncIterator[str]: ...

class EmbeddingsProvider(Protocol):
    def embed(self, texts: list[str]) -> list[list[float]]: ...   # нормализованные векторы
    dim: int

class ASRProvider(Protocol):
    def transcribe(self, audio_path: Path, language: str = "ru") -> Transcript: ...
    # Transcript: segments[{start_ms, end_ms, text, words?[{start_ms,end_ms,word}]}]

class OCRProvider(Protocol):
    def read(self, image_path: Path) -> list[OcrBox]: ...   # text + bbox

class VLMProvider(Protocol):
    async def describe(self, image_path: Path, prompt: str) -> str: ...
```

### 5.2 Структурированный вывод
`complete_json`:
1. Передаёт JSON Schema модели (если сервер поддерживает: `response_format`/guided decoding в vLLM, `format` в Ollama).
2. Валидирует ответ через Pydantic.
3. При ошибке — до 2 повторов с сообщением об ошибке валидации в контексте.
4. После 3 неудач — исключение `LLMStructuredOutputError`; вызывающий код обрабатывает его явно (задача в `jobs` получает статус `failed` с текстом ошибки).

### 5.3 Fake-провайдеры
- `FakeLLM` — возвращает заранее записанные ответы по ключу (хэш промпта или имя шаблона) из `backend/tests/fixtures/llm/*.json`; для неизвестных запросов — детерминированный ответ-заглушку.
- `FakeEmbeddings` — детерминированные векторы из хэша текста (одинаковый текст → одинаковый вектор; пересечение слов → близость).
- `FakeASR` — возвращает транскрипт из соседнего с аудио файла `*.transcript.json`.

### 5.4 Рекомендуемые модели (проверить актуальность на момент разработки)
| Задача | По умолчанию | Альтернативы |
|---|---|---|
| Генерация, извлечение | Qwen-семейство instruct 7–14B (через vLLM/Ollama) | T-lite / T-pro (русскоязычные дообучения Qwen), GigaChat API, YandexGPT |
| Проверка обоснованности | та же модель | более крупная модель, если есть ресурсы |
| Эмбеддинги | `BAAI/bge-m3` | русскоязычные дообучения bge-m3, `intfloat/multilingual-e5-large` |
| ASR | faster-whisper `large-v3` | GigaAM (Сбер, сильна на русском) |
| VLM (опционально) | Qwen-VL 7B | — |

Для разработки без GPU допустимо использовать облачный OpenAI-совместимый endpoint, **но только с вымышленными демо-данными**. В демо обязательно показать, что достаточно переключить `LLM_BASE_URL` на локальный сервер.

```
gaps(id, handover_id, qa_log_id null, question, status [open|answered|dismissed],
     answered_card_id null, answered_by null, answered_at null)

audit_log(id, user_id null, action, entity, entity_id, meta jsonb, at)

jobs(id, type, payload jsonb, status [queued|running|done|failed], attempts int,
     error null, run_after, started_at, finished_at)

events(id, user_id, handover_id null, name, props jsonb, at)   -- продуктовые метрики
```

Индексы: `card_chunks.embedding` (HNSW, cosine), `card_chunks.tsv` (GIN, конфигурация `russian`), `jobs(status, run_after)`, `qa_logs(handover_id, created_at)`.

## 7. Модули

### 7.1 Аутентификация и доступ
- Вход по email + паролю, JWT в httpOnly cookie, срок жизни 12 часов.
- Доступ к данным передачи дел: `admin` — всё; `manager` — передачи своего подразделения; `expert` — передачи, где он эксперт; `successor` — передачи, где он преемник, и **только** подтверждённые карточки, ассистент, свои пробелы.
- Преемник **не видит** черновики, отклонённые карточки и сырые транскрипты интервью; видит фрагмент-цитату, на который ссылается подтверждённая карточка, и видео записи экрана.
- Проверка прав — в одной зависимости FastAPI (`require_handover_access(role_in_handover)`), покрыть тестами.

### 7.2 Передачи дел и процессы
- CRUD передачи дел (manager/admin).
- Процессы создаются руководителем вручную или подтверждаются экспертом в фазе «карта обязанностей» интервью (см. 7.4).
- При создании передачи: эксперт автоматически добавляется в `process_holders` как `owner` для выбранных процессов, преемник — как `learning`.
- Статус передачи `completed` выставляет руководитель вручную.

### 7.3 Согласие и приватность
- Перед первым интервью или записью эксперт видит текст согласия (`backend/app/prompts/consent_v1.md` — хранить версию). Без принятого согласия эндпоинты интервью и записей возвращают 403 с понятным сообщением.
- Текст согласия (черновик, юристы потом поправят): что записывается, зачем, кто видит, где хранится (в контуре организации), срок хранения, право отозвать согласие и удалить данные.
- **Удаление данных** (`DELETE /api/privacy/my-data?handover_id=…` и удаление отдельной записи):
  1. помечает `assets.deleted_at` и физически удаляет файлы;
  2. удаляет транскрипты, сообщения интервью (или заменяет содержимое на `[удалено по запросу сотрудника]` — выбрать удаление), шаги записей;
  3. карточки, у которых **все** источники удалены, переводит в `archived` с `archived_reason='source_deleted'` и убирает из индекса; карточки с частью источников остаются, но удалённые ссылки исчезают;
  4. пишет событие в `audit_log`.
- Отзыв согласия = запрет новых записей + предложение удалить уже собранное.
- Хранение сырых медиа ограничено `RETENTION_DAYS_RAW_MEDIA` (фоновая задача чистки; карточки и скриншоты после размытия остаются).

### 7.4 ИИ-интервьюер

#### Методика
Основа — когнитивный анализ задач (Cognitive Task Analysis) и метод критических случаев (Critical Decision Method): спрашивать не «как вообще делается», а «расскажите про последний раз», «по каким признакам вы поняли», «что было бы, если бы новичок сделал иначе».

#### Аспекты покрытия процесса
Фиксированный список (ключи на английском, подписи на русском):

| key | Подпись | Пример вопроса-зонда |
|---|---|---|
| `purpose` | Зачем и что на выходе | «Для кого этот результат и что будет, если его не сделать вовремя?» |
| `trigger` | Когда запускается | «Что служит сигналом, что пора этим заниматься?» |
| `steps` | Шаги | «Расскажите, как вы делали это в последний раз, по шагам.» |
| `tools` | Системы и инструменты | «В каких программах или таблицах это делается?» |
| `inputs` | Входные данные и документы | «Что нужно получить заранее и от кого?» |
| `done_criteria` | Как понять, что готово | «По каким признакам вы понимаете, что можно отправлять?» |
| `exceptions` | Исключения | «Был ли случай, когда обычный порядок не сработал? Что вы сделали?» |
| `pitfalls` | Типичные ошибки | «На чём чаще всего ошибаются новички?» |
| `contacts` | Люди и контакты | «К кому идти, если что-то пошло не так? Что лучше у него спросить?» |
| `timing` | Сроки и календарь | «Есть ли горячие периоды или жёсткие дедлайны?» |
| `rationale` | Почему так | «Почему делается именно так, а не проще?» |

Статус аспекта: `missing | partial | covered`. Процент покрытия процесса для интервью = `(covered + 0.5·partial) / 11`. (Отдельно на панели считается покрытие **подтверждёнными карточками** — см. 7.9.)

#### Фазы
1. `intro` — приветствие, объяснение формата, напоминание о согласии; один вопрос: «Расскажите коротко, чем вы занимаетесь».
2. `map` — карта обязанностей: собрать список регулярных задач. LLM извлекает кандидаты в процессы → эксперт подтверждает список в UI (чекбоксы, частота, критичность). Подтверждённые процессы создаются/связываются с передачей.
3. `walkthrough` — для текущего процесса: «Расскажите, как вы делали это в последний раз».
4. `deepen` — зонды по непокрытым аспектам текущего процесса.
5. `wrapup` — «Что ещё обязательно должен знать ваш преемник, о чём я не спросил?» → завершение сессии.

Переход между процессами: когда покрытие текущего ≥ 70% или эксперт нажал «Перейти к следующему процессу». Сессии можно ставить на паузу и продолжать; состояние хранится в `interview_sessions.state_json`.

#### Цикл одного хода (2 вызова LLM + детерминированный планировщик)
```
expert_message
   │
   ▼
[1] analyze_turn (LLM, JSON)  ──►  { aspects_touched[], is_vague, vague_reason,
                                     new_processes[], key_facts[] }
   │
   ▼
[2] update_state (код)        — обновить статусы аспектов, список процессов
   │
   ▼
[3] plan_next (код, детерминированно):
      если is_vague            → follow-up «попросить конкретный пример»
      иначе если фаза map и есть неподтверждённые процессы → вопрос/подтверждение
      иначе если текущий процесс < 70% → самый приоритетный missing-аспект
            (порядок: steps → done_criteria → exceptions → pitfalls → inputs →
             contacts → timing → trigger → tools → purpose → rationale)
      иначе → следующий процесс (по убыванию criticality) или wrapup
   │
   ▼
[4] generate_question (LLM, текст) — один короткий вопрос в контексте последних реплик
```
- Планировщик (`plan_next`) — чистая функция от состояния, покрыть юнит-тестами.
- Не задавать один и тот же зонд по одному аспекту больше 2 раз подряд; если эксперт говорит «не знаю/не бывает» — пометить аспект `covered` с флагом `not_applicable`.
- Время ответа на ход: цель < 8 секунд на локальной модели 7–14B.
- Учитывать **активное время** эксперта в сессии (`active_seconds`: суммировать интервалы между сообщениями, отбрасывая паузы > 5 минут).

#### Голосовой ответ
Кнопка микрофона → `MediaRecorder` (webm/opus) → `POST /api/interviews/{id}/audio` → синхронное распознавание для фрагментов до 2 минут (дольше — через job) → текст подставляется в поле ввода → эксперт правит и отправляет. Аудио сохраняется как `asset`, ссылка в `interview_messages.audio_asset_id`.

#### UI интервью
- Слева чат. Справа панель «Покрытие»: список процессов и аспекты с отметками (иконка + текст статуса, не только цвет).
- Кнопки: «Пауза», «Следующий процесс», «Завершить сессию».
- После завершения сессии автоматически ставится job `extract_cards_from_session`.

### 7.5 Извлечение карточек знаний

Job `extract_cards_from_session(session_id)`:
1. Собрать реплики эксперта с контекстом вопросов; разбить на окна по ~3000 токенов с перекрытием в одну реплику.
2. Для каждого окна — `extract_cards` (LLM, JSON): массив карточек
   `{type, process_name, title, summary, body_md, applies_when, quotes: [{message_seq, text}]}`.
3. **Валидация цитат** (защита от галлюцинаций): каждая цитата нормализуется (нижний регистр, `ё→е`, схлопнуть пробелы, убрать пунктуацию по краям) и ищется в тексте указанной реплики через `rapidfuzz.fuzz.partial_ratio ≥ 90`. Цитаты, которые не нашлись, отбрасываются. **Карточка без единой валидной цитаты отбрасывается** и логируется в `events` (`card_dropped_no_evidence`).
4. Привязать карточку к процессу по `process_name` (нечёткое совпадение с процессами передачи; не нашлось — `process_id = null`, эксперт выберет при проверке).
5. **Дедупликация**: эмбеддинг `title + summary`; если косинусная близость ≥ 0.9 с существующей карточкой той же передачи (любого статуса, кроме rejected) — не создавать новую, а добавить источники к существующему черновику или создать черновик-предложение с пометкой «возможный дубль: <id>».
6. Сохранить как `draft` с `card_sources`.

Типы карточек и связь с аспектами:
| type | Подпись | Покрывает аспекты |
|---|---|---|
| `procedure` | Инструкция | steps, tools, inputs, trigger |
| `rule` | Правило / признак | done_criteria, rationale, purpose |
| `exception` | Исключение | exceptions |
| `pitfall` | Типичная ошибка | pitfalls |
| `contact` | К кому обращаться | contacts |
| `deadline` | Сроки | timing |
| `term` | Термин / жаргон | — |

### 7.6 Записи экрана

#### Захват в браузере
- `navigator.mediaDevices.getDisplayMedia({video: true})` + `getUserMedia({audio: true})`, объединить треки в один `MediaStream`, `MediaRecorder` → webm (vp8/vp9 + opus).
- Ограничение 30 минут; таймер на экране; перед стартом — напоминание: «закройте вкладки с личной информацией».
- Альтернатива: загрузка готового видеофайла (mp4/webm/mov) до 1 ГБ.
- Загрузка целиком после остановки (`multipart/form-data`), прогресс-бар.

#### Обработка (job `process_recording`)
1. `ffmpeg`: извлечь аудио (wav, 16 кГц, моно), получить длительность.
2. ASR с таймкодами слов → `transcript_segments`.
3. `segment_recording` (LLM, JSON): по транскрипту с таймкодами выделить шаги
   `{idx, title, action, rationale, start_ms, end_ms}`. Валидация: интервалы внутри длительности, не пересекаются, по возрастанию; при нарушении — исправить кодом (обрезать/сдвинуть) или повторить запрос.
4. Для каждого шага — скриншот кадра в момент `end_ms - 500` (`ffmpeg -ss … -frames:v 1`).
5. Размытие ПДн на скриншоте (7.6.1).
6. (Если `VLM_ENABLED`) короткое описание того, что на экране, для уточнения шага.
7. Создать черновик карточки `procedure`: заголовок = название записи, тело = нумерованные шаги со скриншотами (markdown-ссылки на защищённый эндпоинт картинок), источники = `recording_step` с таймкодами.

#### 7.6.1 Размытие персональных данных
- OCR кадра → боксы со словами.
- Детекторы на тексте боксов: регулярки (телефон РФ, email, СНИЛС `\d{3}-\d{3}-\d{3} \d{2}`, ИНН 10/12 цифр, паспорт `\d{2}\s?\d{2}\s?\d{6}`, номер карты 16 цифр с проверкой Луна) + `natasha` NER для персон (`PER`).
- Сработавшие боксы (с запасом 4 px) размываются Гауссом (OpenCV), оригинал кадра не сохраняется.
- `recording_steps.screenshot_blurred = true`, если хоть что-то размыто; в UI показывать пометку «персональные данные скрыты автоматически».
- Эксперт при проверке может вручную добавить прямоугольник размытия (should, если успеваем).

### 7.7 Проверка карточек экспертом
Экран «На проверке»:
- Список черновиков, группировка по процессам, счётчик.
- Карточка открывается в двух колонках: слева — редактор (заголовок, тип, процесс, «когда применять», тело в markdown с предпросмотром), справа — **источники**: цитаты с подсветкой в контексте реплики интервью; для записей — видеоплеер, который открывается на `start_ms`.
- Действия: «Подтвердить», «Подтвердить с правками» (сохраняет новую версию), «Отклонить» (с необязательной причиной), «Объединить с …» (для дублей).
- Горячие клавиши: `A` — подтвердить, `R` — отклонить, `J/K` — следующая/предыдущая.
- Учитывать время на проверку (`review_seconds`: время, пока карточка открыта и вкладка активна).
- После подтверждения: job `index_card` — разбить тело на чанки (~500 токенов, по абзацам/шагам), посчитать эмбеддинги, `tsv`, записать в `card_chunks`. При правке подтверждённой карточки — переиндексация. При отклонении/архивации — удаление чанков.
- Экспертная правка — главный механизм контроля качества: в UI явно написать «В базу попадёт только то, что вы подтвердите».

### 7.8 Ассистент преемника

#### Поиск
1. Эмбеддинг вопроса.
2. Векторный поиск по `card_chunks` (cosine, top-20) **и** полнотекстовый (`websearch_to_tsquery('russian', q)`, top-20) в пределах передачи дел (и, опционально, всего подразделения).
3. Слияние Reciprocal Rank Fusion (k = 60) → top-8 чанков → группировка по карточкам (до 5 карточек).
4. **Порог релевантности**: если лучший косинус < `RAG_MIN_SIMILARITY` (стартовое значение 0.45 для bge-m3, **откалибровать на eval-наборе**) и нет полнотекстовых совпадений — сразу отказ без вызова LLM.

#### Генерация ответа
- Промпт `answer.md`: источники пронумерованы `[1]…[n]`, в каждом — заголовок карточки, тип, текст. Правила: отвечать только по источникам; каждое утверждение со ссылкой `[n]`; если ответа нет — вывести ровно `NO_ANSWER`; если ответ частичный — ответить на найденную часть и явно сказать, чего в базе нет.
- Ответ стримится через SSE.

#### Проверка обоснованности (после генерации)
1. Разбить ответ на утверждения (предложения со ссылками).
2. Утверждение без ссылки → неподтверждённое.
3. Для каждого утверждения со ссылкой — `verify_claim` (LLM-судья, JSON `{supported: bool, reason}`) с текстом процитированного источника. Батчить утверждения в один вызов, если их до 8.
4. `groundedness = supported / total`.
5. Если есть неподтверждённые утверждения — удалить их из ответа; если после удаления ничего не осталось — отказ. В UI ответ помечается: «Все утверждения подтверждены источниками» или «Часть ответа удалена: не нашлось подтверждения».
6. Всё пишется в `qa_logs` (включая `retrieval` с id и скорами чанков).

Ограничение задержки: цель — ответ до 15 секунд на локальной модели 7–14B (с проверкой). Проверку можно выполнять параллельно со стримингом и показывать отметку после.

#### Отказ и пробелы
- При отказе показать: «В базе знаний нет ответа на этот вопрос. Я передал его [имя эксперта] / руководителю». Автоматически создаётся `gap`.
- Кнопка «Спросить эксперта» есть и под обычным ответом (если ответ не помог).
- Эксперт видит очередь пробелов, отвечает текстом или голосом → ответ превращается в черновик карточки (`origin = gap_answer`, источник — текст ответа) → проходит обычную проверку → после подтверждения `gap.status = answered`, преемник получает уведомление в интерфейсе.
- Если эксперт уже ушёл — пробел видит руководитель и может закрыть его или назначить другого эксперта.

#### UI ассистента
- Чат; под ответом — чипы источников `[1] Название карточки · тип`. Клик открывает боковую панель: карточка целиком + её первоисточники (цитата интервью или видео с нужной секунды).
- Кнопки «Помогло / Не помогло» (+ комментарий).
- Подсказки-примеры вопросов на пустом экране (из заголовков карточек).
- Отдельная вкладка «База знаний»: все подтверждённые карточки с фильтрами по процессу и типу, поиск.

### 7.9 Панель руководителя и карта рисков

#### Прогресс передачи дел
- Дни до дедлайна; проведено интервью (сессий, минут эксперта); записей экрана; карточек: черновики / подтверждено / отклонено; открытые пробелы.

#### Покрытие процесса подтверждёнными карточками
Аспект считается покрытым, если есть ≥ 1 подтверждённая карточка соответствующего типа (таблица в 7.5) по этому процессу. `coverage_approved = covered_aspects / applicable_aspects` (аспекты с `not_applicable` исключаются).

#### Риск по процессу
```
holders = число людей в process_holders с level ∈ {owner, knows},
          не считая эксперта активной передачи дел
holder_factor = 1.0 если holders == 0; 0.6 если holders == 1; 0.3 если holders == 2; 0.1 иначе
deadline_factor = 1.0 если до дедлайна ≤ 14 дней; 0.7 если ≤ 30; 0.4 иначе (нет дедлайна → 0.4)
risk = criticality/3 × holder_factor × (1 − coverage_approved) × deadline_factor
уровень: «Высокий» если risk ≥ 0.35; «Средний» если ≥ 0.15; иначе «Низкий»
```
Функция чистая, покрыть тестами. Пороги вынести в конфиг.

#### Экран
- Таблица «Карта рисков»: процесс · критичность · кто знает (имена) · покрытие (полоса + процент) · открытые пробелы · дедлайн · уровень риска (иконка + слово, не только цвет). Сортировка по риску.
- Тепловая матрица «процессы × аспекты» (покрыт / частично / нет) — should.
- Блок метрик ассистента за период: вопросов, доля отвечено, доля отказов, средняя оценка «помогло», топ-5 открытых пробелов.

### 7.10 Продуктовые метрики и события
Писать в `events` (и считать агрегаты на лету SQL-запросами):

### 9.2 Визуальный стиль
- Шрифт **Inter** (совпадает с шаблоном презентации хакатона), основной акцент `#0A86E0`, светлый акцент `#CFE9FE`, карточки `#F4F4F4`, текст `#1A1A1A` / `#434343`.
- Спокойный деловой интерфейс, без лишних градиентов и анимаций.
- Статусы и уровни риска — всегда иконка + текст, не только цвет.

- Типы API генерировать из OpenAPI бэкенда (`openapi-typescript`) — `make gen-api`.

## 11. Контроль качества ИИ (eval)

Это обязательная часть: жюри требует показать, как контролируется качество.

### 11.1 Наборы данных (`eval/datasets/`)
- `demo_qa.jsonl` — 50–60 вопросов по демо-базе знаний:
  `{"id", "question", "answerable": bool, "expected_answer", "expected_card_titles": [...]}`
  из них **не менее 15 неотвечаемых** (ответа в базе нет, но вопрос правдоподобный), 5–10 «с подвохом» (близкие формулировки к существующим карточкам, но с другим смыслом).
- `demo_extraction_gold.json` — эталонный список фактов (30–40), которые должны попасть в карточки из демо-интервью.

### 11.2 Скрипт `make eval` (`eval/run_eval.py`)
Прогоняет ассистента по `demo_qa.jsonl` на текущих настройках и считает:
| Метрика | Как считается | Целевое значение (ориентир) |
|---|---|---|
| Правильность ответа | LLM-судья сравнивает с `expected_answer` (0/1) на отвечаемых | ≥ 80% |
| Полнота цитирования | доля ожидаемых карточек среди процитированных | ≥ 80% |
| Корректный отказ | доля отказов на неотвечаемых | ≥ 90% |
| Ложные отказы | доля отказов на отвечаемых | ≤ 10% |
| Обоснованность | средняя `groundedness` | ≥ 0.95 |
| Задержка | p50 / p95, мс | p95 ≤ 15 000 |

Извлечение: доля эталонных фактов, найденных в сгенерированных карточках (судья), и доля карточек, отброшенных из-за отсутствия цитат.

Отчёт пишется в `eval/reports/<дата>_<модель>.md` (таблица метрик + список провалов с вопросом, ответом, источниками). Скрипт также подбирает `RAG_MIN_SIMILARITY`: перебирает порог 0.30–0.70 с шагом 0.05 и показывает компромисс «корректные отказы / ложные отказы».

Скрипт должен работать и в режиме `--provider fake` (для CI — проверка, что пайплайн не сломан), и с реальной моделью.

## 12. Безопасность и защита данных

- Развёртывание целиком в контуре организации: БД, файлы, модели. `OFFLINE_MODE=true` запрещает обращения к нелокальным адресам (проверка при старте и в HTTP-клиенте провайдеров: разрешены `localhost`, приватные диапазоны, имена сервисов compose).
- Файлы не имеют публичных URL; отдаются через `/api/assets/{id}` с проверкой прав, поддержкой Range для видео.
- Пароли — `argon2`/`bcrypt`. JWT в httpOnly, `SameSite=Lax`, `Secure` в проде.
- Логи приложения не содержат текстов вопросов, ответов и транскриптов (только id и метрики). Содержимое хранится только в БД.
- Журнал аудита: вход, просмотр записи экрана, подтверждение/отклонение карточки, удаление данных, изменение согласия.
- Минимизация: в профиле пользователя только ФИО, email, роль. Скриншоты — с автоматическим размытием ПДн. Срок хранения сырых медиа ограничен.
- Ограничение размера загрузок, проверка MIME по содержимому (`python-magic`), защита от path traversal в хранилище.
- Отдельный документ `docs/privacy.md` (агент составляет по коду): какие данные собираются, где хранятся, кто видит, как удаляются — для слайда «Защита данных».

### 13.3 Сценарий видео-демо (3–4 минуты)
1. Руководитель: создаёт передачу дел, видит в карте рисков «Отчёт о движении контингента — высокий риск».
2. Эксперт: согласие → 3–4 хода интервью (один голосом), панель покрытия заполняется.
3. Эксперт: запускает запись экрана в mock-portal (или открывает заранее обработанную), показывает шаги со скриншотами и размытыми ПДн.
4. Эксперт: проверка — открыть карточку, увидеть цитату-источник, поправить, подтвердить.
5. Преемник: вопрос → ответ со ссылками → клик → видео с нужной секунды.
6. Преемник: вопрос без ответа в базе → честный отказ → пробел.
7. Эксперт отвечает на пробел → новая карточка.
8. Руководитель: покрытие выросло, риск снизился; метрики.
9. Кадр с отчётом `make eval` (качество ассистента в цифрах) и переключением на локальную модель.

## 14. План работ и критерии приёмки

Даты ориентировочные; при отставании — резать should, а не must.

### M0. Каркас (17–19 октября)
- Репозиторий по структуре 4.3, docker-compose, Makefile (`up`, `down`, `test`, `lint`, `seed-demo`, `eval`, `gen-api`), Alembic, модели БД, аутентификация и роли, fake-провайдеры, `/health`, базовый layout фронтенда и логин.
- **Готово, когда:** `make up` поднимает всё; можно войти под демо-учётками; `make test` зелёный; в CI (GitHub Actions) — lint + тесты на fake-провайдерах.

### M1. Интервьюер и карточки (20–30 октября) — для спринта 1
- Передачи дел и процессы (CRUD), согласие.
- ИИ-интервьюер: фазы, анализ хода, планировщик, генерация вопроса, панель покрытия, голосовой ввод.
- Извлечение карточек с валидацией цитат и дедупликацией.
- Экран проверки карточек (без видео-источников).
- Сид демо-данных (интервью + карточки).
- **Готово, когда:** с реальной LLM эксперт проходит интервью из ≥ 10 ходов, вопросы осмысленные и не повторяются; после завершения появляются черновики, у каждого есть хотя бы одна цитата, которая реально есть в интервью (тест); эксперт может подтвердить/поправить/отклонить; записано видео-демо этой части.

### M2. Ассистент и качество (2–14 ноября)
- Индексация подтверждённых карточек, гибридный поиск, ответ со ссылками (SSE), проверка обоснованности, отказ, пробелы и ответы на них, база знаний.
- Eval-набор и `make eval`, калибровка порога.
- **Готово, когда:** `make eval` выдаёт отчёт; на демо-наборе корректных отказов ≥ 80% и правильных ответов ≥ 70% (дальше улучшаем к целевым из 11.2); клик по ссылке открывает карточку и её первоисточник.

### M3. Записи экрана и ПДн (10–22 ноября)

## 15. Тестирование

Обязательные юнит-тесты (детерминированная логика):
- планировщик интервью `plan_next` (все ветки: vague, map, переход процесса, wrapup, лимит повторов);
- расчёт покрытия (интервью и по подтверждённым карточкам), `not_applicable`;
- валидация цитат (точное совпадение, `ё/е`, пунктуация, отсутствующая цитата → карточка отброшена);
- дедупликация (порог близости);
- RRF-слияние и порог отказа;
- разбиение ответа на утверждения и сборка ответа после удаления неподтверждённых;
- формула риска и уровни;
- детекторы ПДн (регулярки + Луна для карт) и размытие боксов на фикстуре-изображении;
- проверка прав доступа (преемник не видит черновики; эксперт чужой передачи — 403);
- каскад удаления данных;
- валидация шагов записи (обрезка интервалов, сортировка).

Интеграционные тесты (на fake-провайдерах, с реальной Postgres в docker): интервью → извлечение → подтверждение → индексация → вопрос → ответ со ссылкой; вопрос без ответа → отказ → пробел.

Фронтенд: минимальный smoke-тест на сборку; ключевые сценарии проверяются вручную по демо-сценарию.

## 16. Нефункциональные требования
- Запуск одной командой на ноутбуке разработчика (CPU) с внешним LLM endpoint; на сервере с одной GPU 24 ГБ — полностью локально (LLM 7–14B в 4/8 бит + bge-m3 + faster-whisper).
- Ход интервью ≤ 8 с, ответ ассистента ≤ 15 с (p95, локальная модель 7–14B), обработка 10-минутной записи ≤ 10 мин на CPU.
- Все фоновые задачи идемпотентны и переживают перезапуск worker (повтор до 3 раз с экспоненциальной задержкой).
- Корректная работа в последних версиях Chrome и Яндекс Браузера (захват экрана — только они).
